Step 3, grounded premortem. Imagine it is Friday 7pm and the migration failed.

1. The single UPDATE holds a long transaction on a production table.
   - Source: "backfill from the customers table in one UPDATE" on "4M rows".
   - Failure pattern: one statement touches every row, so it holds row locks for its whole runtime, generates a large volume of write-ahead log or undo, and bloats the table. Concurrent orders writes then wait or time out.
   - The rollback is also hurt. If the UPDATE fails or you cancel it late, the database must undo all of its work, which can take as long as the forward run.

2. The DDL step may lock the table.
   - Source: "add a NOT NULL column `region` with default 'unknown'" on a 4M-row table.
   - This is conditional on the engine (question 1). On older versions an ALTER that rewrites 4M rows can block reads and writes for minutes.
   - I can't tell from the plan whether this applies.

3. The rollback loses data.
   - Source: "Rollback: restore last night's backup."
   - A restore returns the database to last night's state, so every order placed between the backup and the failure is lost. The plan does not mention a replay or a point-in-time recovery.
   - Restore time is unstated, so the outage length is unknown. A restore that has never been tested is itself an unverified mechanism.
   - The migration's own failure modes (risks 1, 2 and 4) have cheaper undo paths, such as dropping the column or cancelling a batch. The plan skips them and goes straight to the most destructive one.

4. The backfill can fail or leave wrong data.
   - Source: "backfill from the customers table", with no join key, no handling of unmatched orders, and no null handling stated.
   - If any matching customers.region is NULL and the target column is NOT NULL, the whole UPDATE errors out.
   - Orders with no matching customer keep 'unknown'. That is the same value as "not yet backfilled", so you can't tell a finished backfill from a partial one.
   - Duplicate customer rows could also make the join ambiguous. This depends on the schema, which I haven't seen.

5. Nothing has been tested.
   - Source: "No staging run is planned."
   - Risks 1 to 4 are exactly what a staging run on a copy of the 4M rows would measure: lock time, UPDATE duration, errors and restore time. Skipping it means you find out in production.
